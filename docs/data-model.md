# Модель данных

12 таблиц. Схема ведётся Alembic, текущая ревизия — `b47c9e0d21fa`.
Все таблицы наследуют `TimestampMixin`: `created_at` и `updated_at` (наружу не отдаются).

```
users                        (админы)

teams ──┬─ competition_teams ─── competitions ──┬─ homepage_blocks
        │                                        │
players ─┴─ competition_players ─────────────────┤
        │                                        │
        ├─ game_player_stats ──── games ─────────┘
        ├─ game_events ─────────┤
        └─ game_team_stats ─────┘

media_files                  (реестр загруженных файлов)
```

## Справочники

### `teams` — команды
`name` и `slug` уникальны, `city`, `logo_url`. Slug генерируется транслитерацией
(`app/services/utils.py:slugify`) и в API нигде не принимается — все ручки только по `id`.

### `players` — игроки
`full_name` (индексирован, формат «Фамилия Имя» — отчества хранить негде),
`birth_date`, `position` (перечисление), `grip`, `photo_url`.

Игрок **не привязан к команде напрямую**. Связь только через заявку соревнования,
поэтому один игрок за сезон может играть за разные команды.

### `users` — доступ в админку
`username` (уникален), `hashed_password` (bcrypt), `role`, `is_active`.

## Соревнования и заявки

### `competitions`
`type` (чемпионат или турнир), `name`, `start_date`, `end_date`, `location`,
`logo_url`, `winner_team_id`, плюс два флага показа на сайте:
`show_playoff_bracket` и `show_best_players`.

### `competition_teams` — какие команды участвуют
Уникально по `(competition_id, team_id)`. Никакой статистики не хранит — таблица
считается на лету.

### `competition_players` — заявка
Уникально по `(competition_id, team_id, player_id)`. Хранит `number` (игровой номер)
и `contract`.

**Номер живёт здесь, а не у игрока**: в разных соревнованиях у одного человека
номера разные. Номер в заявке и номер в протоколе матча — тоже разные вещи, и
расхождение между ними допустимо (см. [эксплуатация](operations.md#заявка-и-протокол)).

Дубли номеров внутри одной команды встречаются в реальных данных и ничем не
запрещены: в боевой базе таких групп больше семидесяти.

## Матчи

### `games`
`competition_id` (индексирован), `team_a_id`, `team_b_id`, счёт обеих сторон, `date`,
`time`, `location`, `scan` (снимок бумажного протокола), `video_url`, `stage`,
`status`, `bullet_win_team_id` и три поля сетки плей-офф (`round_no`, `bracket_slot`,
`next_game_id`, заполняются вручную и сервером не валидируются).

**`status` выводится из счёта**: как только заполнены оба счёта, матч становится
`finished` (`game_service._maybe_finish`).

**Счёт хранится за основное время.** Победа по буллитам отмечается отдельным полем
`bullet_win_team_id` — см. [соглашение по буллитам](#буллиты) ниже.

### Протокол матча и таймлайн

Две таблицы, и важно не путать их роли.

**`game_player_stats` — кто играл и вратарские цифры.** Уникально по
`(game_id, player_id)`: одна строка на игрока в матче. Поля: `goals`, `assists`,
`penalties`, `is_goalie`, `goals_against`, `saves`, `minutes_played`.

Два инварианта, которые легко нарушить правкой кода:

1. **`goals`, `assists`, `penalties` — производные.** Они пересчитываются из
   `game_events` внутри `save_protocol`. Извне не принимаются: входная схема
   `PlayerStatLine` их не содержит и с `extra="forbid"` отвергает.
   `penalties` — это **минуты**, а не количество удалений.
2. **Число проведённых игр = число строк.** `stats_service` считает его как
   `count(game_player_stats.id)`. Поэтому строка участия обязана существовать у
   каждого игравшего, даже если у него нули. И наоборот: не вносите в протокол
   того, кто в бумаге отмечен «Иг: нет», иначе ему зачтётся игра.

**`game_events` — хронология.** `game_id` (индексирован), `type`, `team_id`,
`time_seconds`, `sort_order`, `player_id`, две передачи, `penalty_minutes`,
`video_seconds`.

- `video_seconds` читается не только в протоколе матча: по нему собираются моменты
  голов в карточке игрока (`GET /players/{id}/goal-moments`);
- `time_seconds` — **сквозное** игровое время от начала матча, как в бумаге:
  `960` = 16:00, `3600` = 60:00;
- `sort_order` ставит сервер по порядку присланного массива, клиент им не управляет.
  Нужен потому, что события с одинаковым временем реально бывают;
- `period` и `penalty_end_seconds` **не хранятся** — это свойства модели.
  Период считается как `1 if t <= 0 else (t - 1) // 1200 + 1` с потолком 4 для
  овертайма: ровные границы относятся к завершившемуся периоду (20:00 → первый,
  60:00 → третий). Конец удаления — начало плюс минуты;
- события **не ссылаются** на `game_player_stats.id`: при сохранении протокола те
  строки удаляются и создаются заново, их id нестабильны.

**`game_team_stats` — командные итоги матча.** Уникально по `(game_id, team_id)`:
`shots`, `shots_on_goal`, `faceoffs_won`, `conversion_percent`. Все поля необязательные —
матч без введённой статистики просто не имеет строк.

- **штрафных минут здесь нет**: они выводятся из событий. Второе место хранения означало бы
  второй источник истины. В ответе API поле `penalty_minutes` появляется, но считается на лету;
- **реализация хранится готовым процентом (целым, 0…100)**, а не считается. На табло лиги её
  выводят по-разному: в матче 28.08 у одной команды это голы от всех бросков, у другой —
  от бросков в створ. Формулы, которая описывает оба случая, нет;
- проверяется одно соотношение: бросков в створ не бывает больше, чем бросков всего.

Обе коллекции у `Game` объявлены с `cascade="all, delete-orphan"` и `ON DELETE CASCADE`
на уровне БД. `Game.events` дополнительно упорядочена в самой связи
(`time_seconds`, `sort_order`, `id`) — поэтому API отдаёт таймлайн уже отсортированным.

## Прочее

### `media_files`
Реестр загруженного: `filename` (уникален, `secrets.token_hex(16)` + расширение),
`content_type`, `size`, `kind`. Сами файлы лежат в каталоге `MEDIA_DIR`.
Картинки приводятся к WebP и уменьшаются: логотипы до 512 px, фото игроков до 700,
сканы протоколов до 1800. PDF принимается как есть.

### `homepage_blocks`
Что показывать на главной: до трёх блоков, каждый — таблица (`standings`) или сетка
плей-офф (`bracket`) конкретного соревнования, плюс необязательный `title`.

`position` задаёт порядок и проставляется сервером по порядку присланного списка —
клиент им не управляет, как и `sort_order` у событий. Ограничение «не больше трёх»
живёт в сервисе (`MAX_HOMEPAGE_BLOCKS`), в схеме его нет.

FK на соревнование — `ON DELETE CASCADE`: удалили соревнование, блок ушёл вместе с ним.
Пустой заголовок без содержимого никому не нужен.

До ревизии `b47c9e0d21fa` здесь был синглтон `homepage_settings` с двумя флагами.
Миграция перенесла настройку в блоки, а API продолжает отдавать прежние четыре поля,
вычисляя их из блоков — см. [API](api.md#главная).

## Перечисления

Все хранятся строками в `VARCHAR` — `native_enum=False`, **без CHECK-ограничений**
(SQLAlchemy 2.0 по умолчанию их не создаёт). Практическое следствие: расширить
перечисление можно кодом, без миграции, но и сырой SQL запишет в такое поле что угодно.

| Перечисление | Значения |
|---|---|
| `UserRole` | `admin`, `manager` |
| `PlayerPosition` | `вратарь`, `защитник`, `нападающий` — **по-русски**, это значения, а не имена |
| `CompetitionType` | `championship`, `tournament` |
| `GameStage` | `matches`, `quarterfinal`, `semifinal`, `final`, `third_place` |
| `GameStatus` | `scheduled`, `finished` |
| `GameEventType` | `goal`, `shootout_goal`, `penalty`, `goalie_change`, `empty_net` |
| `HomepageBlockType` | `standings`, `bracket` |
| `MediaKind` | `player_photo`, `team_logo`, `competition_logo`, `game_scan`, `other` |

### Буллиты

`shootout_goal` — отдельный тип, а не флаг у гола. Смысл: **сумма событий типа
`goal` по команде равна её `score_team_*`**, и фронту не нужно знать про исключения.
Гол в серии буллитов в счёт матча не идёт, но **в личную статистику игрока идёт**
(решение лиги). Поэтому «сумма голов игроков больше счёта» при буллитной победе —
норма.

Победа в серии отмечается `games.bullet_win_team_id`, и таблица начисляет за неё
дополнительный балл, но **только если счёт ровный**:
`points = wins*2 + draws*1 + extra_points*1`. Записать итог с буллитом (5:4 вместо
4:4 + флаг) — значит лишить проигравшего его балла.

### События вратаря

У `goalie_change` `player_id` — тот, кто **вышел** на лёд. У `empty_net` наоборот —
тот, кого **сняли**. Второй тип появился из реального протокола, где вратаря убрали
на десять секунд.
