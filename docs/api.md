# REST API

Префикс `/api/v1`, 42 ручки. Интерактивная документация — `/docs`, схема —
`/openapi.json` (по ним можно генерировать типы).

> Для фронтенда есть отдельный, более подробный контракт:
> [../API_FRONTEND.md](../API_FRONTEND.md) и
> [../API_FRONTEND_TIMELINE.md](../API_FRONTEND_TIMELINE.md). Этот документ —
> справочник для бэкенд-разработчика.

## Авторизация

**Все `GET` публичны.** Токен нужен только для записи.

```
POST /api/v1/auth/login     форма username + password  →  {access_token, role}
```

Дальше `Authorization: Bearer <token>`. Токен — JWT HS256, живёт сутки
(`ACCESS_TOKEN_EXPIRE_MINUTES`, по умолчанию 1440).

Роли: `admin` — всё, включая управление пользователями; `manager` — контент.
Зависимости в `app/api/deps.py`: `get_current_user`, `require_role`, `require_staff`,
`require_admin`.

Админ-панель авторизуется **иначе** — через cookie-сессию, не через JWT.

## Соглашения

**Пагинация** — только у команд, игроков и соревнований:
`{items, total, page, size}`, параметры `page` (≥1) и `size` (1…200, по умолчанию 50).
Матчи, составы и статистика — **простые массивы без обёртки**.

**Ошибки.** `detail` — строка при `404` и массив объектов при `422`, обрабатывать надо
оба варианта. `500` отдаётся единым телом `{"detail": "Внутренняя ошибка сервера",
"code": "internal_error"}` через глобальный обработчик в `app/main.py`.

**Форматы.** Дата `YYYY-MM-DD`, время `HH:MM:SS`, отсутствующие значения — явный
`null`, поля из JSON не пропадают.

**Без слэша на конце.** `/api/v1/teams`, не `/api/v1/teams/` — иначе `307`.

**Ссылки на файлы относительные**: `/media/<hash>.webp`.

## Соревнования

| Метод | Путь | Что делает |
|---|---|---|
| `GET` | `/competitions` | `Page<Competition>` |
| `GET` | `/competitions/{id}` | соревнование |
| `GET` | `/competitions/{id}/teams` | состав по командам |
| `GET` | `/competitions/{id}/players` | заявка со статистикой |
| `GET` | `/competitions/{id}/standings` | турнирная таблица, уже отсортирована |
| `GET` | `/competitions/{id}/best-players` | бомбардиры, параметр `limit` |
| `GET` | `/competitions/{id}/games` | матчи соревнования |
| `POST` `PUT` `DELETE` | `/competitions[/{id}]` | создать, изменить, удалить |
| `POST` | `/competitions/{id}/teams` | заявить команду |
| `DELETE` | `/competitions/{id}/teams/{team_id}` | убрать команду |
| `POST` | `/competitions/{id}/players` | заявить игрока |
| `PATCH` | `/competitions/{id}/players/{player_id}` | изменить номер или контракт |
| `DELETE` | `/competitions/{id}/players/{player_id}` | убрать игрока из заявки |

**Таблица считается только по регулярке** (`stage = matches`) и только по матчам с
двумя заполненными счетами. Бомбардиры, наоборот, считаются по всем стадиям —
числа в двух блоках закономерно не сходятся.

Строки таблицы создаются только для команд, **заявленных** в соревнование: если
команду не заявили, её не будет в таблице даже при сыгранных матчах.

## Матчи

| Метод | Путь | Что делает |
|---|---|---|
| `GET` | `/games` | список, параметры `competition_id`, `team_id`. **Без протокола** |
| `GET` | `/games/{id}` | матч + `player_stats` + `events` |
| `POST` `PUT` `DELETE` | `/games[/{id}]` | создать, изменить, удалить |
| `PUT` | `/games/{id}/protocol` | заменить протокол целиком |

`team_id` в списке матчит команду с любой стороны. Сортировка: дата → время → id.

### `PUT /games/{id}/protocol`

Заменяет протокол **целиком**. Тело:

```json
{
  "score_team_a": 4, "score_team_b": 4, "bullet_win_team_id": 4,
  "stat_lines": [
    {"player_id": 517, "team_id": 4, "is_goalie": true,
     "goals_against": 4, "saves": null, "minutes_played": 60},
    {"player_id": 527, "team_id": 4}
  ],
  "events": [
    {"type": "goal", "team_id": 4, "time_seconds": 960, "player_id": 527,
     "assist1_player_id": null, "assist2_player_id": null, "video_seconds": 2705},
    {"type": "penalty", "team_id": 4, "time_seconds": 757, "player_id": 9,
     "penalty_minutes": 2}
  ]
}
```

Плюс командные итоги матча — те самые цифры для карточки «итоги матча»:

```json
  "team_stats": [
    {"team_id": 5, "shots": 41, "shots_on_goal": 34,
     "faceoffs_won": 9, "conversion_percent": 17},
    {"team_id": 2, "shots": 37, "shots_on_goal": 17,
     "faceoffs_won": 16, "conversion_percent": 23}
  ]
```

В ответе у каждой строки добавляется `penalty_minutes` — он **не хранится**, а
считается из событий матча. Реализация, наоборот, только хранится: сервер её не
пересчитывает (на табло её выводят то от всех бросков, то от бросков в створ).
`team_stats` ведёт себя как `events`: `null` — не трогать, `[]` — стереть.

Три вещи, которые надо знать:

1. **`goals`/`assists`/`penalties` в `stat_lines` не принимаются.** Схема с
   `extra="forbid"`, так что старый клиент получит внятную `422`, а не молчаливое
   обнуление. Эти числа сервер выводит из `events`.
2. **`events` отсутствует (`null`) = «не трогать таймлайн»**, а `[]` = «очистить и
   обнулить производные цифры». Без этого различия сохранение протокола без событий
   стирало бы всю хронологию.
3. **События проверяются целиком, включая уже сохранённые.** Если новый состав не
   содержит автора уже записанного гола, сохранение упадёт с `400` — осиротевших
   событий не бывает.

Валидация командных итогов: команда участвует в матче, одна строка на команду,
бросков в створ не больше, чем бросков всего.

Валидация событий (все ошибки → `400` с русским текстом): команда события участвует в матче;
каждый упомянутый игрок имеет строку участия за ту же команду; передачи только у
голов, не равны автору и друг другу, вторая не без первой; у буллита передач не
бывает; у удаления обязательны минуты; у событий вратаря игрок должен быть отмечен
`is_goalie`; время в пределах `0…7200`.

## Медиа и главная

| Метод | Путь | Что делает |
|---|---|---|
| `POST` | `/media` | загрузка файла, `multipart` + поле `kind` |
| `GET` | `/media/<filename>` | статика, отдаётся напрямую |
| `GET` `PUT` | `/homepage` | блоки главной |

Принимаются `image/jpeg`, `png`, `webp`, `gif` и `application/pdf`, лимит
`MAX_UPLOAD_MB` (10). Картинки перекодируются в WebP и уменьшаются по типу.

### Главная

`GET /homepage` отдаёт блоки в порядке показа, каждый с вложенной карточкой
соревнования — фронту не нужен второй запрос за названием:

```json
{
  "blocks": [
    {"id": 1, "position": 1, "type": "standings", "competition_id": 2,
     "title": "Таблица Спорта",
     "competition": {"id": 2, "type": "tournament", "name": "Летний кубок (Спорт)",
                     "logo_url": null}},
    {"id": 2, "position": 2, "type": "bracket", "competition_id": 3, "title": null,
     "competition": {"id": 3, "type": "tournament", "name": "Летний Кубок (Дебют)",
                     "logo_url": null}}
  ],
  "show_standings": true, "standings_competition_id": 2,
  "show_bracket": true, "bracket_competition_id": 3
}
```

Блоков не больше трёх, `title` пустой — фронт берёт название соревнования.

**Четыре поля внизу — прежний вид настроек.** Они остались, чтобы не ломать уже
написанный фронт, и **выводятся из блоков**: берётся первый блок каждого типа.
Новый код должен читать `blocks` — только там видны второй и третий блоки.

`PUT /homepage` принимает `{"blocks": [...]}` и **заменяет набор целиком**; `[]`
очищает главную, а отсутствие поля означает «не трогать». Прежний вид тела
(`show_standings` и остальные три) тоже принимается и переводится в блоки: сначала
таблица, потом сетка. `position` не передаётся — порядок берётся из массива.
Больше трёх блоков → `422`, несуществующее соревнование → `400`.

## Пользователи

`GET` `POST` `/auth/users`, `PUT` `DELETE` `/auth/users/{id}` — только для роли
`admin`. Плюс `GET /auth/me`.

## Служебное

`GET /health` → `{"status": "ok"}` (используется healthcheck'ом контейнера и внешним
мониторингом), `GET /` → название и версия сервиса.
